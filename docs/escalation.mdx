When the watchdog detects a failure and finishes diagnosing, it escalates to you. This
is the **Agency** rung of the ladder: you're notified, and you decide.

## What you receive

A single **Telegram message** from the keepalive bot, containing:

1. A one-line diagnosis of the failure.
2. **Inline buttons** — ⏪ Roll back, 🔧 Apply fix, 🛑 Stop — plus a **🧵 View trace** URL
   button whenever a Weave trace link exists.
3. An **AI voice note** that arrives as an actual voice bubble in the chat. The library
   sends a `voice_script` string to the relay; the relay synthesizes the `gpt-4o-mini-tts`
   mp3 with its own OpenAI key, hosts it, and pulls it into a `sendVoice` call so the
   explanation plays inline — no link to a hosted page. TTS is best-effort: if it fails, the
   text message still arrives.

## Reply semantics

Tap a button **or** type a single digit — both record the same reply:

| Button | Type | Meaning | What keepalive does |
| ------ | ---- | ------- | ------------------- |
| **⏪ Roll back** | **1** | Rollback | Raises `KeepaliveRollback(checkpoint)` — roll back to the last good checkpoint. |
| **🔧 Apply fix** | **2** | Apply fix | Applies the agent's top fix and resumes. |
| **🛑 Stop** | **3** | Stop | Raises `KeepaliveStop` — halt training cleanly. |

See [control exceptions](/reference/watchdog#control-exceptions) for how your code should
catch these.

<Note>
Button taps carry `"{incident_id}:{choice}"` in their `callback_data`; a typed 1/2/3 is
resolved through the relay's `active:{chat_id}` mapping. Either way the library polls the
relay for the reply.
</Note>

## Deadlines and authority transfer

When the incident is escalated, keepalive arms a deadline and polls for your reply every
couple of seconds. Two outcomes:

- **You reply in time** → keepalive does what you asked (1/2/3).
- **The deadline expires** → authority transfers. keepalive stops waiting and moves to
  the autonomous **Assurance** rung: it spawns probes and races fixes. See
  [probes](/probes).

The timeout is configurable. The default is 120s (`KEEPALIVE_TIMEOUT` /
`timeout=` on `watchdog()`); for a live demo, drop it to ~20s for pacing.

By default the deadline is an **in-process timer** — no Redis required. It lives in the
training process alongside the watchdog, so it won't survive a process restart; that's fine,
because if the training process dies there's no run left to wait on. When `REDIS_URL` is set
(power-user / self-host), the deadline is armed in a **Redis ZSET** (`keepalive:deadlines`)
instead, with the same behavior.

<Note>
When Redis is in play, ZSET polling is the reliable mechanism. Redis keyspace `Ex` expiry
notifications are best-effort and are used only as demo flair, never as the source of truth.
</Note>

## Why Telegram

We moved escalation from SMS to a Telegram bot. The wins:

- **No carrier / A2P filtering** of link-bearing messages — Weave-trace and voice-note
  links go through untouched.
- **No phone-number verification** dance. The user presses Start once and the bot replies
  with their chat id.
- The voice note **plays inline** as a voice bubble instead of forcing a tap-through to a
  hosted audio page.
- **Buttons beat typing codes** — one tap to roll back, apply, or stop.
- Webhook auth is **one shared-secret header** (`X-Telegram-Bot-Api-Secret-Token`) instead
  of HMAC signature validation.

## Telegram caveats (self-hosters)

If you run your own relay, mind these:

- **The user must press Start first.** A Telegram bot cannot send the first message to a
  user who has never started a chat with it. The Start handler replies with the chat id and
  the `KEEPALIVE_TELEGRAM_CHAT_ID=<id>` line to copy.
- Inbound updates (button taps and typed replies) arrive at the relay's `/telegram` webhook.
  The relay validates the `X-Telegram-Bot-Api-Secret-Token` header against
  `TELEGRAM_WEBHOOK_SECRET`.
- To test the inbound path, just `curl` the `POST /telegram` webhook with the secret header
  — no tunnel and no real device needed.

Full setup in the [self-hosting guide](/self-hosting).
